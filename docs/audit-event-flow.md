# 变更审计事件写链路与版本链设计

本文对应"变更审计追踪"从业务动作到审计记录的数据流，以及乱序事件按版本键还原的规则。
实现入口：

- `backend/app/services/audit_hooks.py` — 业务动作 → 审计写入的统一钩子
- `backend/app/services/audit_ledger.py` — 事件账本：幂等、归并、版本链、结果投影
- `backend/app/audit_seed.py` — 故意乱序到达的示例事件
- `backend/tests/test_audit_events.py` — 行为测试

## 1. 业务动作到审计记录的写入调用链

```text
前端页面（audit / catalog / retention / lifecycle）
  │  POST {模块}/{id}/actions  ·  POST retention/{id}/duration
  ▼
routers/{module}.py
  │  只做参数解包，不做状态判断
  ▼
services/{module}.py  run_action / update_duration / create_entry
  │  ① 校验必填字段与动作是否属于本模块
  │  ② 读取业务行当前值，得到"变更前值"
  │  ③ 调用审计钩子，先落账、后回写业务行
  ▼
services/audit_hooks.py  apply_status_action / record_field_change
  │  组装事件：来源模块、业务对象编号/主键、变更对象、变更类型、
  │            变更前值/后值、操作人、操作时间、复核状态、复核人
  ▼
services/audit_ledger.py  AuditLedger.ingest
  │  ① 归一化时间与字段，缺少必填字段直接拒绝
  │  ② 幂等键命中 → 结论一致则"重放"（不追加）；结论不一致则拒绝
  │  ③ 检查对象内事件序号槽位：
  │       · 同槽位 + 同结论 + 落库时间在归并窗口内 → 合并到原事件
  │       · 同槽位 + 不同结论 → 顺延为下一事件序号（后到者不覆盖）
  │  ④ 分配本地序列号、落库批次号、幂等键摘要、校验码
  │  ⑤ 写事件并重建：字段版本链 → 对象事件链 → 生命周期结果
  ▼
services/audit_ledger.py  attach_source_event / lifecycle_results
  │  列表行补来源事件、入口标记、版本链摘要、派生复核状态
  ▼
前端列表 / 历史链面板 / 生命周期结果清单
```

### 关键约束

| 约束 | 实现位置 |
| --- | --- |
| 相同事件重放不追加副本 | `ingest` 幂等键分支：`_by_idem` 命中即返回原事件 |
| 重放不得出现两个结论 | `_same_conclusion` 比对前后值、操作时间、复核状态；不一致返回冲突 |
| 并发争抢同一版本槽位只生效一次 | `threading.RLock` 串行化槽位判断；后到者 `冲突后补版本` 顺延 |
| 后到旧事件不能覆盖已复核结论 | 复核状态按 `已记录 → 已复核 → 已归档` 取最大，结果投影单调前进 |
| 归档后仍能按原序列读取 | `_archived_ids` 只标记存储分区，`chains` / `history` 不排除归档事件 |
| 同一秒事件可区分 | 稳定排序键 `对象#变更对象#事件序号#本地序列号` |

## 2. 版本流程图

```text
                        ┌──────────────────────────────┐
业务事件（可乱序到达）   │ AUDI-0001 / 参数阈值          │
  v2: 90→100  ─────────►│  arrival #3                  │
  v1: 80→90   ─────────►│  arrival #6（后到）           │
                        └──────────────┬───────────────┘
                                       │ 分组键 = 业务对象编号 + 变更对象
                                       ▼
                        ┌──────────────────────────────┐
                        │ 版本键 AUDI-0001|参数阈值      │
                        │ 事件序号 1  / 本地序列号 6      │
                        │ 事件序号 2  / 本地序列号 3      │
                        └──────────────┬───────────────┘
                                       │ 按事件序号排序（不看到达顺序）
                                       ▼
             ┌─────────────────────────────────────────────┐
             │ v1  事件序号 1  80 → 90   已记录  父序号 0    │
             │ v2  事件序号 2  90 → 100  已复核  父序号 1    │
             └──────────────┬──────────────────────────────┘
                            │ 三种投影，读同一份链
        ┌───────────────────┼────────────────────┐
        ▼                   ▼                    ▼
  事件流水列表        版本链 / 稳定排序键      生命周期结果清单
  (账本顺序)          (链指纹 + 只读校验戳)    (当前值 + 单调复核状态)
```

### 乱序断点定位

每条事件额外保存到达态元数据：

- `到达时前序事件序号`：事件落库那一刻，对象内序号小于它的最新事件。
- `到达时前序值`：该事件的"变更后值"。
- `到达即接续`：`到达时前序值 == 本次变更前值` 时为真。
- `断点标记`：接不上时写明"乱序到达：变更前值未接上到达时最新版本，已按事件序号归位"。

于是"`变更前值` 接不上"从数据缺陷变成可查询的诊断字段，而版本链本身始终正确。

## 3. 归并窗口与版本键

- **版本键** `业务对象编号|变更对象`。同一对象的参数阈值、负责人、复核状态各自成链，
  互不干扰；对象内共用一个事件序号空间，便于还原完整操作历史。
- **归并窗口** 默认 120 秒，按 `落库时间` 计算。同槽位、同结论的事件在窗口内合并，
  只累加 `合并计数`，不新增行。窗口外的同槽位冲突不会覆盖，而是顺延下一版本。
- **本地序列号** 单调递增，与业务事件序号解耦，保证即使两个模块给出同样的序号，
  存储层仍能稳定区分先后。
- **落库批次戳** `落库时间@落库批次号`，用于跨月归档后按批回放。

## 4. 前端稳定顺序

审计页所有列表都走账本稳定排序键：`对象编号 → 事件序号 → 本地序列号 → 主键`。
刷新页面、切换筛选、归档后重新读取，顺序都不会变化；业务页面的"来源事件"列
显示最新事件编号与入口标记，点开即可看到同一条版本链。

## 5. 示例事件链预期

| 对象 | 链路 | 验证点 |
| --- | --- | --- |
| AUDI-0001 | `参数阈值 80→90`（事件 1）→ `90→100`（事件 2） | v2 先到，仍排为 v2 |
| AUDI-0003 | `负责人 甲→乙`（事件 1）→ `复核状态 已记录→已复核`（事件 2）→ `负责人 乙→丙`（事件 3） | 旧负责人事件晚到，复核状态不回退 |
| CATA-0003 | `负责人 甲→乙`（8/31 操作，9/1 落库）→ `乙→丙`（事件 2） | 跨月归档后仍按事件序号读取 |
| RETN-0003 | `保留期限 180→90`（事件 1）→ `90→30`（事件 2） | 两条操作时间同为 09:30:00，靠稳定排序键区分 |
